## はじめに — 「島」を作る場所が決まらない

J-SIX はこれまで、既存システムへの適用を2つの記事で扱ってきました。[#5 段階的移行](https://zenn.dev/seckeyjp/articles/j-six-05-migration)は開発プロセスを Stage 0 から Stage 3 へ移す話、[レガシーコード × Claude Code](https://zenn.dev/seckeyjp/articles/j-six-legacy-code)は変更したい箇所をテストで囲んで「島」を作る話です。

どちらも、**変更する箇所を選んで囲める**ことを前提にしています。大規模なモノリスでは、この前提が成り立たないことがあります。著者の見解では、Claude Code（以下 CC）を持ち込むときの障害は次の4つです。

| 障害 | 起きること |
|---|---|
| 文脈に収まらない | 全体を読ませることができない。どこまで読めば足りるのかも決まらない |
| 変更の影響範囲が閉じない | 共通クラスや共有テーブルを通じて、変更がどこへ波及するか分からない。「ここだけ触ってよい」と AI に言えない |
| テストが無い | 変更の前後で振る舞いが同じかを確かめる手段がない |
| 設計書が Excel にある | 仕様の根拠を AI が直接読めない。人が読んで、要約して渡すことになる |

この記事は、この4つを**システムの構造**の側から解く構想を書きます。既存の2記事との分担は次のとおりです。

| 記事 | 扱う移行 | 単位 |
|---|---|---|
| #5 段階的移行 | 開発プロセス（V字から J-SIX へ） | 組織・案件 |
| レガシーコード × Claude Code | コードの改修の進め方（特性化テスト、腐敗防止層、Strangler Fig） | 変更する箇所 |
| **本記事** | システムの構造と、既存設計書の取り込み | システム全体・モジュール |

想定する既存システムは Java の業務システムです。考え方は言語を限定しませんが、手段の例は Java で示します。

## 1. 到達点: モジュラーモノリス

到達点は**モジュラーモノリス**に置きます。デプロイの単位は1つのまま、内部を明示的な境界を持つモジュールに分けた構成です。モジュールは、公開するインターフェース、所有するデータ、依存してよい相手を持ち、境界を越える参照はビルドやテストで止まります。

### モジュール境界が AI に与えるもの

人間にとってのモジュール境界は、理解と分担の単位です。AI にとっては、次の4つの単位になります（著者の見解）。

| 単位 | 内容 |
|---|---|
| 読み込む文脈 | モジュールの中と、依存先が公開するインターフェースだけを読めば作業できる |
| タスクの許可範囲 | 変更してよいファイルを、モジュール単位で宣言できる |
| テストと設計書 | 回帰テストと設計書をモジュールにひも付けられる。変更したモジュールの分だけ確認すればよい |
| 並列作業 | 境界をまたがないタスクは、互いを壊さずに並列で進められる |

1つ目には、CC の側に受け皿があります。CC は、サブディレクトリに置いた `CLAUDE.md` を、そのディレクトリのファイルを読み書きするときに読み込みます。`.claude/rules/` に置いた規則は、対象のファイルをパスで絞れます[^claude-memory]。モジュールごとの説明と注意を、そのモジュールを扱うときだけ読ませることができます。

「はじめに」の4つの障害のうち、前の2つは境界があれば解けます。残りの2つ（テスト、設計書）は、境界に沿って整備する対象になります。

### マイクロサービスを到達点にしない理由

Martin Fowler は、成功したマイクロサービスの事例のほぼすべてが、大きくなりすぎたモノリスを分割したものだった、と書いています。最初からマイクロサービスで作ったと聞いた事例は、ほぼすべてが深刻な問題に陥った、とも書いています[^fowler-monolith]。Shopify は、Ruby on Rails の大きなコードベースについて、マイクロサービスにも固有の課題があるとして、1つのコードベースのまま境界を定めて守らせるモジュラーモノリスへ進化させる方針を選び、その経過を公開しています[^shopify]。

著者の見解として、AI が扱えるようにするという目的に限れば、必要なのは**境界**であって、**デプロイの分割**ではありません。上の4つの単位は、1つのデプロイ単位の中の境界で得られます。デプロイを分けると、ネットワーク越しの呼び出し、データの整合、運用の負担が加わります。境界の引き方を誤ったときの直しも、サービスをまたぐ分だけ重くなります。

マイクロサービスを否定する主張ではありません。モジュラーモノリスに到達したあとで、必要なモジュールだけを切り出す選択は残ります。

## 2. 経路: 移行段階 M0〜M3

到達点までの経路は、4つの**移行段階**に区切ります。どの段階で止めても、そこまでの成果が残るように区切っています。

```mermaid
flowchart LR
  M0["M0<br>現状把握"]
  M1["M1<br>AI が扱える土台"]
  M2["M2<br>物理的な分離"]
  M3["M3<br>モジュラーモノリス"]
  M0 -->|"棚卸しと<br>渡せる範囲の確認"| M1
  M1 -->|"対応表・回帰テスト・<br>設計書の MD 化"| M2
  M2 -->|"既存の違反を<br>減らす"| M3
```

| 段階 | 名称 | 行うこと | ここで止めた場合に得るもの | 設計書の正本 |
|---|---|---|---|---|
| M0 | 現状把握 | コード・テーブル・バッチ・設計書の棚卸し。顧客の資料を AI に渡してよい範囲の確認 | 資産の一覧と、AI に渡せる範囲の合意 | 既存の Excel/Word |
| **M1** | **AI が扱える土台** | 論理モジュール分割、回帰テストによる現行の振る舞いの固定、Excel 設計書の MD 化、設計書・コード・振る舞いの突き合わせ | モジュール単位で AI に文脈と許可範囲を渡せる。変更の前後を比較できる。設計書を AI が読める | 既存の Excel（MD は派生物） |
| M2 | 物理的な分離 | 対応表に合わせて、パッケージやビルド単位を移す。固定した既存の違反を減らす | 境界がコードの構造として見える | 未検討 |
| M3 | モジュラーモノリス | すべての境界違反をビルドで止める。テスト・設計書・並列作業をモジュール単位にする | 到達点 | 未検討 |

この記事の中心は **M1** です。M1 では**コードの配置を動かしません**。M2 と M3 は7章で概要だけ書きます。

### 既存の「Stage」「Step」との関係

J-SIX には、似た呼び名の区切りが既に2つあります。この記事の移行段階は、どちらとも別の軸です。

| 軸 | 呼称 | 何を移すか | 定義している場所 |
|---|---|---|---|
| プロセス | Stage 0〜3 | 開発プロセス（V字 → V字+CC補助 → ハイブリッド → J-SIX） | 記事 #5 |
| コードの改修 | Step 1〜4 | 変更する箇所ごとの進め方（理解 → テストで囲む → 島を作る → 島を広げる） | j-six の `docs/guide-legacy-code.md`、記事 #5 |
| システムの構造 | 移行段階 M0〜M3 | モジュールの境界と、既存設計書の扱い | 本記事（構想） |

Step の名称は、j-six のレガシーコード適用ガイド[^jsix-guide-legacy]の定義を使いました。記事「レガシーコード × Claude Code」は、Step 3 を腐敗防止層（Anti-Corruption Layer）、Step 4 を Strangler Fig による段階的置換として説明しています。ガイドでは、この2つは Step 3「島を作る」の実装パターンに含まれます。

3つの軸は並行して進められます。ガイドの移行マップは、Step 1 を Stage 1、Step 2 と Step 3 を Stage 2、Step 4 を Stage 3 に置いています[^jsix-guide-legacy]。これに移行段階を重ねた目安は次のとおりです（構想）。

| 移行段階 | 並行して進める Step | ガイドの移行マップでの Stage |
|---|---|---|
| M0 | Step 1（理解）を、システム全体に対して行う | Stage 1 |
| M1 | Step 2（テストで囲む）を、変更する箇所からモジュールの入出力へ広げる | Stage 2。対応表と設計書の MD 化はテストもコードも変えないので、Stage 1 のうちに始められると考える |
| M2・M3 | Step 3（島を作る）と Step 4（島を広げる）を、対応表のモジュールの中で行う | Step 3 は Stage 2、Step 4 は Stage 3 |

M2・M3 の行に置いたのは、構造の移行に伴う Step 3・4 です。M1 で止めた場合も、通常の改修は Step 3 として進められると考えます。範囲は準備の整ったモジュールの中、自律度は3章で決める上限までです（構想）。

### M0: 現状把握

M0 で作るのは一覧です。ソースコード、テーブル、バッチ、帳票、設計書のファイルを数え、置き場所と管理者を書き出します。

もう1つ、**顧客の資料とデータを AI に渡してよい範囲**を確認します。設計書、ソースコード、本番データから作ったテストデータのそれぞれについて、契約と顧客の規程で渡せるか、どのサービスや環境なら渡せるかを確かめます。ここが決まらないと、M1 の設計書の取り込みと回帰テストは始められません。

## 3. 移行段階 M1 その1: 論理モジュール分割

### コードを動かさずに、所属だけを決める

M1 では、本番コードの配置（パッケージ）とビルド単位を変えません。境界の検査と回帰テストのための依存やプラグインは、ビルド設定に足します。ファイル・テーブル・バッチが**どのモジュールに属するか**を、機械可読な対応表として持ちます。

テストの無いモノリスでコードを移すのは危険です（著者の見解）。対応表なら、境界の引き方を誤っても表を直すだけで済みます。そして AI に文脈と許可範囲を渡す目的には、対応表で足ります。

次は対応表の形式の案です。**この記事の提案であり、J-SIX にも Plugin にも実装していません。**

```yaml
# modules.yaml（形式の案。未実装）
modules:
  - id: billing
    name: 請求
    paths:                       # このモジュールに属するファイル
      - src/main/java/com/example/app/billing/**
      - src/main/java/com/example/app/common/dao/Invoice*.java
    tables: [INVOICE, INVOICE_DETAIL]   # 所有するテーブル
    batches: [BL010]                    # 所有するバッチ
    design_docs:
      - docs/design/基本設計書_請求.xlsx
    depends_on: [customer, common]      # 依存してよいモジュール
    readiness:                          # 準備状況（後述）
      regression_tests: partial
      design_md: done
    autonomy_max: L2
baseline: boundaries-baseline.json      # 固定した既存の違反
```

`paths` の2行目のように、ほかのパッケージに置かれたファイルも、動かさずにモジュールへ割り当てます。

### 分割の手がかり

| 手がかり | 見るもの |
|---|---|
| 機能一覧 | 既存の設計書にある機能の区分、サブシステムの区分 |
| パッケージ構成 | 既存のパッケージと命名規則 |
| データの読み書き（CRUD） | テーブルごとに、どの機能が作成・参照・更新・削除をしているか |
| バッチの流れ | ジョブの前後関係と、受け渡す中間ファイルやテーブル |

**AI が案を作り、人が決めます。** CC にコードと設計書を読ませて、根拠（ファイル、テーブル、設計書の該当箇所）を付けた分割案を出させます。どの案を採るかは、システムを知っている人が決めます。決めた理由は ADR に残します。境界の引き方に唯一の正解は無く、対応表はあとで変えられる前提で作ります。

### 共有 DB と「共通」の扱い

大規模なモノリスでは、どの機能も同じテーブルを読み書きし、「共通」と名の付いたパッケージに業務ロジックが入っていることがよくあります（著者の見解）。M1 ではこれを直しません。次のように扱います。

- **テーブルには所有モジュールを1つ決める。** ほかのモジュールからの読み書きは「境界違反」として記録する。止めない
- **「共通」を2つに分けて割り当てる。** 業務を持たない本当の共通部品は、すべてのモジュールが依存してよい `common` モジュールにする。業務ロジックは、ファイル単位で該当するモジュールに割り当てる
- **既存の違反は基準値として固定し、新しい違反だけを止める。** 対応表を作った時点の違反を一覧にして保存する。以後の検査は、一覧に無い違反が増えたときだけ失敗させる

3つ目は、既にある手法です。Java の ArchUnit は、既存の違反を記録して、以後は新しい違反だけを報告する `FreezingArchRule` を備えています。ArchUnit のユーザーガイドは、育ったプロジェクトに規則を入れると、すぐには直せない数の違反が出ることが多い、と動機を説明しています[^archunit]。Shopify が Rails アプリケーション向けに公開している Packwerk も、既存の違反を一覧のファイルに記録できます[^packwerk]。

### Java での手段の例

外部のツールは、2026-11-22 に公式の文書で機能を確認したものだけを挙げます。**この記事のために実行はしていないので、コードと設定は載せません。**

| 目的 | 手段の例 | 条件・注意 |
|---|---|---|
| 依存の抽出 | JDK 8 以降に付属する `jdeps`[^jdeps]。クラスファイルの、パッケージ単位またはクラス単位の依存関係を表示する | 対象はクラスファイルに現れる依存に限られると考える（著者の理解） |
| 境界の検査 | ArchUnit[^archunit]。Java のバイトコードを解析して、パッケージやクラスの間の依存、循環の有無を検査する | ユーザーガイドは、Java 8 のプロジェクトのような古いコードベースにも使えると述べている |
| 既存違反の固定 | ArchUnit の `FreezingArchRule`[^archunit] | 記録した違反の保存先を、リポジトリで管理する |
| モジュール構造の検証 | Spring Modulith[^modulith]。モジュールの間に循環が無いことなどを検証する | 公式の紹介記事は Spring Boot 3.0・Java 17 を基準にすると述べている。それより古い環境のシステムは対象にならないと考える（著者の理解） |

クラスファイルやバイトコードの解析は、リフレクションによる呼び出し、設定ファイルで結ばれた依存、SQL の文字列の中のテーブル参照を拾わない場合があります（著者の見解）。テーブルの読み書きは、SQL やマッパーの定義から別に洗い出す必要があります。

### 準備状況に応じて自律度を上げる

J-SIX は、CC に任せる度合いを自律度 L0〜L4 の5段階で定義しています[^jsix-main]。既存のレガシーコード適用ガイドは、理解に L1、テストで囲む作業に L2、新規コードの TDD に L3 を割り当て、自律度を L3 にいきなり上げることを、やってはいけないこととして挙げています[^jsix-guide-legacy]。

この考え方を、モジュール単位に当てはめます（構想）。対応表にモジュールごとの準備状況を持たせ、自律度の上限を決めます。

| モジュールの準備状況 | 自律度の上限（案） |
|---|---|
| 対応表に載っただけ | L1（人が主導し、CC が読解を補助する） |
| 境界の検査が動いており、変更する箇所を回帰テストで囲んでいる | L2（CC が案を作り、人が毎回承認する） |
| 加えて、回帰テストの十分性を確認し、設計書との突き合わせを済ませている | L3（CC が自律実行し、人が結果を監督する） |

L4 はこの記事では扱いません。J-SIX は L4 の条件を、品質ゲート G1〜G4 の全層通過と定めています[^jsix-main]。既存コードのモジュールでその条件を満たす方法は、検討していません。

## 4. 移行段階 M1 その2: 回帰テストで現行の振る舞いを固定する

### 関数単位で囲めない場合

「レガシーコード × Claude Code」は、関数やクラスの単位で特性化テスト[^feathers]を書く方法を扱いました。大規模なモノリスでは、DB 接続やフレームワークに強く結び付いていて、クラスを単体で動かせない箇所があります（著者の見解）。その場合は、外側の入出力で囲みます。

| 粒度 | 固定するもの | 比較の方法の例 |
|---|---|---|
| バッチ | 入力のファイルとテーブル、出力のファイルと更新後のテーブル | 実行結果を保存しておき、再実行した結果と比べる |
| DB | 処理の前後でのテーブルの差分 | DB を既知の状態にして処理を実行し、期待するデータと比べる（DbUnit[^dbunit] など） |
| 帳票 | 出力した帳票のデータ | 保存しておいた出力と比べる |
| 画面・API | リクエストに対する応答 | 承認済みの出力と比べる（ApprovalTests[^approvaltests] など） |

### 非決定性、テストデータ、現行のバグ

- **日付と時刻**: 業務日付を外から与えられる仕組みがあれば固定する。無ければ、比較から外す項目を一覧にして管理する。外す項目を黙って増やさない
- **採番**: 連番を初期化してから実行するか、比較の前に置き換える
- **並び順**: 順序が保証されない出力は、並べ替えてから比べる
- **テストデータ**: 本番データから作る場合は、匿名化と持ち出しの合意が要る。AI に渡してよいかは M0 で確認した範囲に従う
- **現行のバグ**: 回帰テストは、現行の振る舞いをバグも含めて固定する。バグらしい振る舞いを見つけても、ここでは直さない。6章の確認事項に回す

### 十分性の確認

囲んだつもりでも、テストが実際には何も確かめていないことがあります。

- **カバレッジ**（Java では JaCoCo[^jacoco] など）で、変更する範囲が実行されているかを見る
- **変異テスト**（Java では PIT[^pit] など）で、コードを意図的に変えたときにテストが落ちるかを見る

J-SIX のサンプルシステムでは、カバレッジ 99% のコードの mutation score が 91.8% で、生き残ったミュータントから本物のテストの穴が見つかりました（J-SIX の既存の実測。[mutation testing の記事](https://zenn.dev/seckeyjp/articles/j-six-mutation-testing)）。カバレッジだけでは十分性は分かりません。

大規模なモノリスの全体に変異テストをかけるのは、時間の面で現実的でないことが多いと考えます（著者の見解）。変更するモジュールに絞ります。J-SIX の品質ゲート G2 は、mutation score の判定を変更したファイルに限定できます（`.jsix-checks.json` の `scope: "changed"`。実装済み）[^jsix-plugin]。

### TDD のゲートとの違い

J-SIX の TDD は、受入テスト（hold-out）、Red、Green、Refactor の順に進み、Red の時点にタグを付けて、以後のテストの弱体化を検出します（実装済み）[^jsix-plugin]。

特性化テストには **Red がありません。** 現行のコードに対して書くので、最初から通ります。そのため「失敗するテストを先に書いた」という起点が作れず、今の TDD サイクルにはそのまま乗りません。特性化テストのためのタスク種別が要ると考えています（構想）。

- 起点は Red のタグではなく、**テストを固定したコミット**にする
- 通過の条件は「テストが通ること」ではなく、**コードを変えたらテストが落ちること**（変異テスト）にする
- 固定したあとのテストは、TDD のテストと同じように弱体化から守る

## 5. 移行段階 M1 その3: Excel 設計書を AI が読める形にする

### 既存の原則と向きが逆になる

ここは、既存の J-SIX の原則と**向きが逆**になります。先に整理します。

J-SIX は、コード・受入テスト・Spec・ADR から工程成果物（Markdown）を逆生成し、これを正とします。顧客様式の設計書は工程成果物を束ねた「ビュー」で、直接編集しません。Excel や Word への変換物も直接編集しません（Plugin の `plugin/skills/doc-reverse-gen/SKILL.md` の概要と出力ルール5[^jsix-skill]、記事「[設計書逆生成の実装](https://zenn.dev/seckeyjp/articles/j-six-doc-reverse-gen)」の4章と9章）。記事 #5 の Stage 3 も、設計書を「逆生成のみ」としています。

この記事の提案は、**既存の Excel を正本にして、Markdown を派生させ、修正は Excel へ書き戻す**ものです。

| | 既存の原則（実装済み） | この記事の提案（構想） |
|---|---|---|
| 対象 | コード・受入テスト・Spec・ADR から逆生成して作る設計書 | 既存システムについて、顧客と合意済みの既存の Excel/Word 設計書 |
| 正本 | 工程成果物（Markdown） | 既存の Excel（原本） |
| 派生物 | 顧客様式の設計書と、その Excel/Word 変換物 | セル番地付きの MD と、全セルの情報を持つファイル |
| 修正の方法 | 逆生成元を直して、作り直す | 原本の Excel にセル単位で書き戻して、MD を作り直す |

2つは対象が違います。既存の原則が直接編集を禁じているのは、**逆生成した設計書とその変換物**です。この記事が書き戻す先は、**顧客と合意した既存設計書の原本**です。「正本だけを直し、派生物は作り直す」という考え方は、どちらも同じです。

M0・M1 で Excel を正本のままにする理由は3つあります（著者の見解）。

1. 顧客が承認しているのは Excel である。正本を替えるには、顧客との合意が要る
2. Excel から MD への変換は情報を落とす（図形、色、レイアウト）。MD は原本の代わりにならない
3. 顧客のレビューと納品は、当面 Excel のまま続く

この記事の提案を適用する範囲は、既存設計書の、移行段階 M0・M1 です。新規に開発する部分は、既存の原則（工程成果物が正、設計書は逆生成）のままにする、というのがこの記事での線引きです（構想。J-SIX の Skill は適用する範囲を限定していません）。レガシーコード適用ガイドの移行マップは、レガシー部分を J-SIX の品質に引き上げる Stage 3 で、設計書を「3層戦略」としています[^jsix-guide-legacy]。M2 以降で既存設計書の正本を切り替えるか、切り替える条件は何か、既存の機能を改修した部分の設計書をどちらで扱うかは、**検討していません。**

### セル番地付きの MD と、全セルの情報の2層

Excel 設計書は、1枚のシートに複数の表、結合セル、欄外の注記が置かれた、方眼紙のような作りであることが少なくありません（著者の見解）。そのまま表に変換しても読めず、どのセルの値だったのかも分からなくなります。

そこで2層に分けます。次の形式は**この記事の提案であり、未実装です。**

**1層目: 読むための MD。** AI と人が読みます。見出しを含む値ごとにセル番地を付けます。例では、F 列は空のセルなので載せていません（照合の対象は空でないセルだけです）。

```markdown
<!-- source: 基本設計書_請求.xlsx / sheet: 項目定義 / sha256: (原本のハッシュ) -->
## シート: 項目定義

### 請求ヘッダ {B4:G4}

| 項目名 {B5} | 型 {C5} | 桁 {D5} | 必須 {E5} | 備考 {G5} |
|---|---|---|---|---|
| 請求番号 {B6} | 文字列 {C6} | 10 {D6} | ○ {E6} | 採番規則は別紙 {G6} |
| 請求日 {B7} | 日付 {C7} | 8 {D7} | ○ {E7} | 業務日付 {G7 取り消し線・コメントあり} |
```

**2層目: 全セルの情報。** 機械が照合と書き戻しに使います。値、数式と計算結果、結合の範囲、表示形式、文字の色や取り消し線、塗りつぶし、コメント、非表示の行と列を、セルごとに持ちます。次の例は抜粋で、見出しのセルなどを省いています。

```json
{
  "source": {"file": "基本設計書_請求.xlsx", "sha256": "(原本のハッシュ)"},
  "sheets": [{
    "name": "項目定義",
    "merged": ["B4:G4"],
    "cells": {
      "B6": {"value": "請求番号", "type": "string"},
      "D6": {"value": 10, "type": "number"},
      "G7": {"value": "業務日付", "type": "string", "strike": true, "comment": "第3版で削除"}
    }
  }]
}
```

1層目だけでは、原本へ戻れません。2層目だけでは、読めません。

取り消し線やコメントのように、読み方を変える属性を持つセルには、1層目にも印を付けます（例の G7）。印が無いと、削除された記述を有効な仕様として読んでしまうからです。印の書き方と、印を付ける属性の範囲は、まだ決めていません。

### 機械的な抽出と、AI による意味づけを分ける

- **抽出は決定論的なプログラムで行う。** 2層目は、Excel を読むライブラリで機械的に作る（Java なら Apache POI[^poi]、Python なら openpyxl[^openpyxl]）。同じ原本からは同じ結果になる
- **意味づけは AI が行う。** どの範囲が1つの表か、どの行が見出しかを AI が判断して、1層目の MD を組み立てる
- **取りこぼしを機械的に照合する。** 2層目にある空でないセルは、1層目に番地付きで現れるか、「未収録」の一覧に理由付きで載るかのどちらかでなければならない。1層目の値は、2層目の同じ番地の値と一致しなければならない

AI が値を書き換えたり、セルを落としたりしていないことを、AI に頼らずに確かめるための分離です。J-SIX は既に、生成物の確認について「機械抽出は抽出規則の範囲、LLM記述は意味と網羅性」を確かめると定めています[^jsix-status]。同じ考え方です。

Excel や Word を Markdown に変換する既存のツールもあります（Microsoft の MarkItDown[^markitdown] など）。MarkItDown の README は、出力はテキスト分析のツールが読むためのもので、忠実度の高い変換には最適でない場合がある、と断っています。書き戻しに必要な**セル番地との対応**を保つかどうかは、README からは確認できませんでした。

### セル単位の書き戻しと、再抽出による一致確認

設計書を直すときは、MD を編集しません。**セル単位の変更依頼**を作り、原本に適用します。

1. 変更依頼は「シート、セル番地、変更前の値、変更後の値」の組にする
2. **人間が変更依頼を承認する。** 原本を退避する
3. 原本の該当セルが「変更前の値」と一致するときだけ書き込む
4. 書き込んだ原本から2層を作り直し、前の2層目との差が、依頼したセルだけであることを確かめる

### 書き戻しのリスクと、扱えない範囲

未検証のリスクが2つあります。

**1つ目: ライブラリは、保存のときに対応していない要素を落とす場合があります。** openpyxl の公式文書は、Excel ファイルのすべての要素を読むわけではないので、既存のファイルを開いて同じ名前で保存すると図形（shapes）が失われる、と警告しています[^openpyxl]。Apache POI の公式文書も、制限事項の一覧は不足している機能のすべてではない、と断っています[^poi]。

**2つ目: 落ちた要素を、手順4の再抽出では検出できない場合があります。** 再抽出で比べるのは、抽出の対象にした要素だけです。図形など対象にしていない要素が消えても、差には現れません。図形を含むファイルでは、変更依頼の一覧を人に渡して Excel で直してもらう運用に切り替えることを考えています。

この2つがあるので、書き戻しは人間の承認と原本の退避を前提にします。AI が顧客の合意済みの文書を、承認なしに書き換える運用は想定しません。

2層に入らないものもあります。

- **図形と画像**: 図形で描いた画面遷移図や帳票レイアウトは、セルの情報に現れない。「未収録」の一覧にシート名を載せ、人が内容を補う
- **色と取り消し線の意味**: 2層目は属性を記録する。赤字が「今回の変更」なのか、取り消し線が「削除」なのかは案件ごとの決め事で、人が凡例を定める
- **顧客の資料を AI に渡すこと**: 契約と顧客の規程の確認が先である（M0）

### Word 設計書

Word の設計書にも、同じ2層の考え方が当てはまります。位置の単位は、セル番地の代わりに、見出し・段落・表のセルになります。読むための MD に位置を付け、全情報を別のファイルに持ち、照合と書き戻しを位置の単位で行います。読み書きの手段には、Java の Apache POI[^poi] や Python の python-docx[^python-docx] があります。旧形式（.doc）には制約があります。python-docx は Word 2003 以前の .doc を開けません。Apache POI も、.doc の書き込みは限定的だと説明しています[^poi]。Word の形式の案は、この記事では示しません。

## 6. 移行段階 M1 その4: 設計書・コード・振る舞いを突き合わせる

M1 のここまでで、3つのものが手に入ります。設計書の MD（設計書が何と言っているか）、コード（どう書かれているか）、回帰テストの記録（実際にどう動くか）です。三者を突き合わせると、食い違いが出ます。

| 食い違い | 例 | 確認すること |
|---|---|---|
| 設計書にあり、コードに無い | 設計書の項目が、どの画面にも帳票にも現れない | 未実装か、廃止されたのか |
| コードにあり、設計書に無い | 設計書に書かれていない分岐がある | 設計書の更新漏れか、不要なコードか |
| 設計書と振る舞いが違う | 設計書は端数を切り捨てると書き、実際の出力は四捨五入になっている | どちらが正しいのか |

**AI はどちらが正しいかを決めません。** 食い違いを、根拠（設計書のセル番地、コードのファイルと行、テスト名）を付けた**顧客への確認事項**の一覧にします。J-SIX の設計書逆生成も、不明な箇所を `[要確認]` と明示し、推測で補わないと定めています[^jsix-skill]。

顧客の回答によって、行き先が分かれます。

- 設計書が古い → 5章の書き戻しで、設計書を直す
- コードが誤っている → 改修のタスクにする。新しい振る舞いは TDD で書く
- 当面そのままにする → 既知の食い違いとして ADR に記録する

決まるまでは、現行の振る舞いを回帰テストで固定したままにします。

## 7. J-SIX と Plugin との関係

既にあるものと、これから足すものを分けます。左の列は j-six の main（`1101258`）で確認した内容です[^jsix-plugin][^jsix-status]。右の列は構想で、実装していません。

| 要素 | 既にあるもの（実装済み） | これから足すもの（構想） |
|---|---|---|
| タスクの許可範囲 | G1 のスコープ検査。変更したファイルを、許可と拒否の glob と照合する | 対応表から、タスクごとの許可リストを作る |
| 境界の検査 | 無い | 新しい違反だけを止める検査を、G1 の検査として扱う取り決め |
| 振る舞いの固定 | TDD サイクル、Red タグを基準にしたテスト改変の検出、カバレッジと mutation score の判定 | 特性化テストのためのタスク種別（Red の無いサイクル） |
| 設計書の生成 | 工程成果物27点の逆生成と、顧客様式への組立。Excel/Word は Markdown からの変換の手順を定めるだけで、専用の変換器は同梱していない | 既存の Excel を読む向き（2層の抽出、照合、書き戻し） |
| 設計書の正本 | 工程成果物（Markdown）が正。設計書と変換物は直接編集しない | 既存設計書に限り、M0・M1 では Excel が正。MD は派生物 |
| 自律度 | L0〜L4 の5段階 | モジュールの準備状況で上限を決める |
| レガシーコード | Step 1〜4 のガイド | Step を進める範囲を、対応表のモジュールで区切る |

Plugin は「ツールを呼ばず、契約を決める」設計です。言語ごとのツールを Plugin が直接呼ぶのではなく、設定ファイルが宣言したコマンドと成果物の形式（JUnit XML、SARIF など）に従い、標準の形式の解析としきい値の判定だけを行います[^jsix-plugin]。境界の検査と Excel の抽出も、特定のツールに固定せず、結果の形式を取り決める方向で検討します。Excel/Word を読み書きする部品を Plugin に同梱するかは、決めていません。

### M2 と M3 の概要

- **M2 物理的な分離**: 対応表に合わせて、パッケージやビルド単位（Maven のマルチモジュール[^maven]、Gradle のマルチプロジェクト[^gradle]）へコードを移す。移すたびに、M1 の回帰テストで振る舞いが変わっていないことを確かめる。基準値として固定した既存の違反を、1つずつ減らす
- **M3 モジュラーモノリス**: 固定した違反が無くなり、すべての境界違反がビルドで止まる。テスト・設計書・並列作業がモジュール単位になる

手順の詳細と、M2 以降の設計書の正本は、今後の検討とします。

## 8. 限界と未検証の事項

- **実案件に適用していません。** 規模のあるシステムでの実証もありません。効果（工数、品質、期間）の数値は示せません
- **対応表、2層の MD、書き戻し、特性化テストのタスク種別は、どれも未実装です。** 形式は案であり、変わります
- **Java 以外は検討していません。** COBOL や PL/SQL が中心のシステムでは、依存の抽出と境界の検査の手段が変わります
- **境界の引き方の正しさは保証しません。** 対応表は人が決め、あとで変える前提です
- **共有 DB は M1 では分けません。** 所有を決めて、違反を記録するところまでです
- **クラスファイルやバイトコードの解析で拾えない依存があります。**（3章）
- **回帰テストは正しさを保証しません。** 保証するのは、現行の振る舞いからの変化の検出です
- **書き戻しでライブラリが落とす要素があり得ます。** 図形と画像、色の意味は2層で扱えません（5章）
- **Word の形式の案は示していません。**
- **M2 以降の設計書の正本と、切り替える条件は未検討です。**
- **外部のツールは公式の文書で機能を確認しただけで、この記事のために実行していません。** 本文に書いた条件のほかに、各ツールが必要とする Java の版は確認していません。古い Java のシステムに使う前に、公式の文書で確かめてください

J-SIX 本体にこの構想のガイドを置いたときに内容が食い違えば、本体を正として、この記事を直します。

## 明日からできること

1. **棚卸しと、渡してよい範囲の確認（M0）。** 設計書・コード・データのそれぞれを AI に渡してよいか、契約と規程を確かめる
2. **機能を1つ選び、対応表を書いてみる。** ファイル、テーブル、バッチ、設計書を1つのモジュールとして書き出す。書けない箇所が、境界のあいまいな箇所である
3. **バッチを1本選び、入力と出力を保存する。** もう一度実行して、同じ出力になるかを比べる。ならない項目が、非決定性の一覧の最初の行になる

どれも、コードを変えずに始められます。

## まとめ

- 大規模なモノリスで AI が扱いにくい理由は、文脈、影響範囲、テスト、設計書の4つである
- 到達点はモジュラーモノリスに置く。AI に要るのは境界であり、デプロイの分割ではない
- 経路は移行段階 M0〜M3 に区切る。最初の M1 ではコードを動かさず、対応表、回帰テスト、設計書の MD 化、三者の突き合わせで**土台**を作る
- 既存の違反は基準値として固定し、新しい違反だけを止める
- 既存の Excel 設計書は、M0・M1 では正本のままにする。AI はセル番地付きの MD を読み、修正はセル単位で原本へ書き戻す。J-SIX の逆生成の原則とは対象が違う
- 食い違いは AI が裁かず、顧客への確認事項にする

この記事は構想です。J-SIX 本体のガイドと Plugin への取り込み、合成の Java 題材での検証は、これから進めます。結果は続編で報告します。
